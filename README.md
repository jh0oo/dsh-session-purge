# dsh-session-purge · 删除会话

在侧边栏「工作区」上方新增一个 **删除会话** 入口。点开后列出工作区内的全部会话，勾选后一键删除。

删除是**两阶段**的：先移入回收站（可完整还原），在回收站里点「彻底删除」或等它到期，才会真正清除
磁盘上的会话目录、投影缓存、会话策略、工作区登记与成本记账。

> 与官方「归档」的区别：归档只是把会话从列表里藏起来，文件仍在磁盘上。
> 本插件的「彻底删除」是不可逆的硬删除；而「删除」只是移到回收站。

### 交互

| 操作 | 行为 |
| --- | --- |
| 单击一行 | 选中该会话（行内出现勾选框高亮） |
| 再次单击同一行 | 取消选中 |
| 右上角 **全选** | 一次选中全部可删除会话；已全选时按钮变为 **取消全选** |
| 右下角 **删除** | 未选中任何会话时置灰；选中后点击弹出确认框 |
| 确认框左侧灰色 **取消** | 关闭弹窗，不做任何改动 |
| 确认框右侧红色 **确认** | 把选中的会话移入回收站 |
| `Esc` | 关闭确认框 |
| 行内 **运行中 / 当前会话** 标签 | 该行不可选，点击会提示原因 |
| 页签 **回收站** | 切换到已删除会话列表 |
| 回收站行 **还原** | 把该会话放回原位（字节、标题、工作区位置一并恢复） |
| 回收站行 **彻底删除** | 弹出确认框，确认后不可恢复地清除 |
| 回收站 **清空回收站** | 一次性彻底删除回收站里的全部会话 |

确认框标题固定为 **是否确认删除此会话**，正文列出将被移动的记录范围，并列出将要删除的会话标题，
超过 6 个时折叠为「…以及另外 N 个会话」。弹窗会抢焦点、把 Tab 限制在弹窗内，关闭后焦点回到原处。
回收站的彻底删除沿用同一套弹窗，只是标题与正文换成不可恢复的措辞。

## 回收站

回收站目录：`~/.dsh/storages/dsh-session-purge/trash/`，索引文件 `index.json`。

- **保留期**默认 30 天（`config.trashRetentionDays`，钳制在 1–3650 天）。到期条目在下次打开回收站时自动清除。
- **还原**会把会话日志目录、投影缓存、会话策略原样搬回去，并向工作区登记重新挂上该会话，
  连同它原来的归档 / 置顶状态一起恢复。字节完全一致，不是重新生成。
- 移入回收站的**同一时刻**就会清理工作区登记和记账，所以回收站里的会话不会出现在侧边栏、
  不会参与成本统计，也不会再被定时任务指到。
- 到期时间不可读的条目**永远不会被自动清除**——宁可留着，也不误删。

## 彻底删除到底清除了什么

每个被选中的会话会依次处理：

1. **宿主释放** —— 先让 Harness 自身把该 agent/session 从内存登记中摘除（`agents.detachEntered` /
   `sessions.detachEntered`），确保写入者已关闭，进程内也不再有隐藏引用。
2. **工作区登记** —— 从 `storages/workspace.json` 的 `tables.workspaces[*].sessionIds` 移除，
   并从 `global.archivedSessionIds` / `global.pinnedSessionIds` 中移除。
3. **会话日志目录** —— 删除 `~/.dsh/sessions/<slug>/<sessionId>/`（内含 `session.v4.jsonl.zstd`），
   若所属 slug 目录变空则一并清理（最多上溯 3 层，且在 `~/.dsh`、`sessions`、`storages` 处停下）。
4. **投影缓存** —— 删除 `storages/session_projcache/sessions/<id>.json`（侧边栏标题的来源）。
5. **会话策略** —— 删除 `storages/vision_router_session_policy/policies/<id>.json`。
6. **工作区账本** —— 见第 2 步。
7. **成本记账** —— 从 `storages/cost-meter/ledger.json` 的 `days[*].sessions[]` 里剔除该会话的记账行，
   并删除 `usageCursors` 中属于它的游标。
8. **上下文概览缓存** —— 从 `storages/dsh-context/overview-cache.v1.json` 的 `sessions[]` 里按 id 剔除条目。
9. **定时任务引用** —— 从 `storages/schedule.json` 的 `involvedSessionIds` 中移除；若某任务的
   `target.sessionId` 正好指向被删会话，会把它改指向该任务自带的保留目标（`session-schedule-<sha256>`），
   **任务本身保留**，不会被静默删除。
10. **无主附件** —— 只删除「被选中会话引用、且没有任何存活会话再引用」的附件（按 sha256 引用计数）。

### 有意不动的东西

- **你在自己的工作区里创建的文档**。会话的 cwd 是你自己的目录，「从未存在过」不能成为删除用户文档的理由。
- **按天聚合的成本统计**（`days[*]` 的 `input` / `output` / `cost` 等）。那是账户层面的历史，不是某个会话的私有数据。
- **定时任务本身**。见第 9 步。

## 安全设计

| 关卡 | 作用 |
| --- | --- |
| 整批预检 | 只要有一个会话不可删（运行中 / 当前会话 / 路径越界 / 正在写入），**整批都不动**，不会删一半 |
| 活跃判定 | 有 agent 在 running，或内存 store 仍持有该会话，一律拒绝 |
| 当前会话 | 你正在对话的那个会话永远不能删 |
| 静默检查 | 读取日志文件 size+mtime 两次（间隔 240 ms），仍在变化就判定为正在写入并拒绝 |
| 路径围栏 | 目标必须位于 `sessions/` 或 `storages/` 之下，且不得指向插件自己的存储目录 |
| 单一入口 | 只注册一个 POST 路由，非 POST 一律 405；只接受来自回环地址的请求 |
| 显式确认 | 破坏性方法必须带 `confirm: true`，否则 400 拒绝 |
| 不注册 tool | 没有给模型的删除工具，也没有命令，唯一入口是界面 |
| 幂等 | 会话目录已不存在时视为「已清干净」，而不是报错 |
| 删除顺序 | 先除名、后删字节：登记表留着 id 而日志已删，会让宿主下次启动 fatal；反过来只是孤儿日志 |

### 删除顺序（0.1.6 起）

这一条不是体验优化，是**能不能启动**的问题。

宿主开机时会遍历工作区登记表的每个成员，逐个读会话头校验
（`WorkspaceRegistry.init` → `indexStoredHeaders` → `attachSession`）。会话头读不到就抛
`cannot validate session '<id>': session persistence holds no such session`，宿主把它当 fatal，
应用直接起不来。所以两种「半截状态」代价完全不同：

| 残留形态 | 后果 |
| --- | --- |
| 登记表有 id、日志已删 | 下次启动 **fatal load failure**，应用打不开 |
| 日志还在、登记表没这行 | 只是孤儿日志，侧边栏看不见，可随时清扫 |

因此 `purge` 与 `trash` 的顺序固定为
**宿主释放 → 登记表除名 → 投影缓存/会话策略 → 会话目录（或移入回收站）**，
`restore` 反过来先还字节再 `attachSession`。`test/order.test.mjs` 在 `detachSession` 被调用
的瞬间回查日志是否仍在磁盘上，把「顺序」而不是「结果」锁住。

**除名失败就不删。** 插件通过宿主 API 除名时会先把条目摘掉、再落盘账本；这两步都可能
被宿主拒绝（条目已被别处改动、账本被占用）。此时代码不会「尽力而为地继续删字节」——
它会强制重写一次磁盘账本（`forceDetach`），若重读后登记表**仍**命名该会话，就直接放弃删除
并报告失败。宁可留下一个删不掉的会话，也不制造一个让人开不了机的状态。
`test/guard.test.mjs`（17 条断言）用一个「拒绝除名」的假 registry 把这条边界钉死。

### 还原也不能乱挂（0.1.8 起）

删除要小心，还原同样会出人命——而且死法更隐蔽。

`attachSession()` 是 async 方法。对一个**宿主不认识**的 id 调它，它会 `await` 之后
`throw`。如果调用方漏了 `await`，这个 rejection 就绕过了外层 `try/catch`，以 unhandled
rejection 的形式打到宿主进程上，下一次启动同样是 `fatal load failure`。0.1.7 及更早
版本在 `restore()` 里就是这么写的。

现在有两道锁：

| 锁 | 做法 |
| --- | --- |
| 认识的才挂 | `hostKnows(id)` 先问 `ctx.sessionPersistence.stat(id)`；宿主不认识就只还原文件、跳过挂载，并在结果里说明「重启后会按磁盘重新收录」 |
| async 全部 await | `attachSession`、`detachSession` 一律 `await`；`detachFromRegistry()` 自己也变成 async，两个调用点同步补上 await |

`test/restore-unknown.test.mjs` 用 23 条断言锁住三种情形：宿主不认识的 id 绝不传给
`attachSession`（断言调用次数为 0）、认识的照常挂载、以及一个**真的会 reject** 的
`attachSession` 被接住并降级成警告。把 `await` 拿掉重跑，该测试会立刻报
`the rejection did not escape as unhandled` 失败。

### 应用起不来时：`tools/repair-ledger.mjs`

这个插件不可能修「已经起不来」的机器——插件本身要在宿主启动完成后才加载。宿主的
`recoverPendingMutation` 只处理未完成的工作区创建，不会清理悬挂成员。所以仓库里带了一个
独立的急救脚本，**不依赖插件运行**：

```bash
node tools/repair-ledger.mjs              # 只体检，有问题退出码 1
node tools/repair-ledger.mjs --apply      # 真正修复
node tools/repair-ledger.mjs --apply --home "D:\other\.dsh"
```

它做三件事，全部是「删掉指向不存在会话的引用」，不碰任何存活数据：

| 步骤 | 处理对象 |
| --- | --- |
| 剔除悬挂成员 | `workspace.json` 的 `tables.workspaces[*].sessionIds`、`global.archivedSessionIds`、`global.pinnedSessionIds` 中日志已不存在的 id |
| 清理孤儿索引 | `storages/session_projcache/sessions/` 与 `storages/vision_router_session_policy/policies/` 下指向不存在会话的记录，**含 `.bak.<stamp>` 变体** |
| 收拾目录 | 空的会话目录与空的 slug 目录 |

退出码：`0` 干净或已修复，`1` 发现问题但未 `--apply`，`2` 路径不对（没有 `storages/`），`3` 异常。
写入同样走 `.tmp` + 退避重试 + 原子改名，与插件本体一致。

### 写入健壮性（0.1.4 起）

宿主 `dsh-storage-json` 的 `writeAtomic` 在 Windows 上曾因 `rename` 撞 `EPERM/-4048`（杀软/索引器瞬时占用）
而直接 fatal。本插件不重蹈覆辙，写入账本时四层保护：

| 层 | 做法 |
| --- | --- |
| 临时文件同构 | 与宿主一致用 `.${randomUUID()}.tmp`，写完再 `rename` |
| 退避重试 | `EPERM/EACCES/EBUSY/EAGAIN/EMFILE/ENOENT` 按 60 ms 起指数退避，共 6 次 |
| 快照比对 | 读时记下 `mtimeMs`+`size`，写前若被他人改动则放弃本次写入（`STALE`）并重来 |
| 写后校验 | 写完重读，确认目标 id 真已消失；不通过则再跑一轮 |

保证的是「会收敛」而非「必然赢」——没有任何实现能战胜在你最后一次校验读取之后才落盘的外部写入。
目录删除同样有 4 轮退避，并在失败时提示关闭杀毒软件实时扫描。

## 安装

```bash
# 在插件目录下打包（tarball 必须带 package/ 前缀）
tar -czf dsh-session-purge-0.1.10.tgz --transform 's,^,package/,' \
  index.js client.js lib locale cordis.patch.yml icon.svg README.md CHANGELOG.md LICENSE package.json test tools
```

然后用插件管理器的 `install_bundle` 指向该 tgz，或在桌面端「设置 → 插件」里选择本地包。

## 结构

```
index.js             宿主入口：建服务、挂一个 POST 路由
client.js            客户端：侧边栏图标 + 主面板（含回收站页签）+ 确认弹窗 + toast
lib/http.js          单条 POST 路由，回环校验、confirm 校验、方法分派
lib/service.js       策略层：整批预检、附件引用计数、宿主释放、回收站编排、残留复查
lib/store.js         文件层：会话目录/缓存/策略的增删、四个账本的条件写与校验
lib/trash.js         回收站：索引、移入、还原、彻底删除、到期清扫、路径围栏
tools/repair-ledger.mjs  急救脚本：应用起不来时在终端清理悬挂登记与孤儿索引
locale/{zh,en}.json  插件市场条目文案
test/                七套测试，全部隔离在临时 DSH_HOME
```
